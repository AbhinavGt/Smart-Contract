# Bugfix Plan — Offline Fallback Mislabeling & Fail-Loud Default

## Context
Testing revealed that when Ollama is unreachable, the pipeline silently substitutes a deterministic, rule-based fallback for both explanations and fixes — but reports this output with the same "✅ Confident" and "✅ Verified" labels used for genuine LLM-generated output. This is misleading and would silently corrupt eval numbers (Step 20/29) if a run happened to occur while Ollama was down. This plan makes the fallback impossible to mistake for real model output, and changes the default behavior to fail loudly rather than silently degrade.

---

## Bug: Fallback output is indistinguishable from genuine LLM output in reports and JSON

### Symptom
Console log shows `Ollama unavailable; using deterministic offline explanation: <urlopen error [Errno 111] Connection refused>`, but the resulting report shows `✅ Confident (critic loops used: 1)` and `✅ Verified — gates passed: ...` with no indication that a rule-based fallback (not the LLM) produced the content.

### Root Cause
The code path that catches the Ollama connection failure returns a deterministic/templated string and proceeds through the rest of the pipeline (critic loop, verification gates) as if it were normal LLM output, without setting any flag that downstream reporting code can check.

### Fix Part 1 — Add an explicit fallback flag that propagates through the whole pipeline

In whichever module wraps the LLM call (likely `src/llm/ollama_client.py` or `src/llm/llm_client.py`):

```python
class LLMResult:
    def __init__(self, text: str, is_fallback: bool, fallback_reason: str = None):
        self.text = text
        self.is_fallback = is_fallback
        self.fallback_reason = fallback_reason

def generate(self, prompt: str) -> LLMResult:
    try:
        response = self._call_ollama(prompt)
        return LLMResult(text=response, is_fallback=False)
    except ConnectionError as e:
        fallback_text = self._deterministic_fallback(prompt)
        return LLMResult(text=fallback_text, is_fallback=True, fallback_reason=str(e))
```

- Every call site that currently does `explanation = llm.generate(prompt)` and treats the return value as a plain string needs to be updated to handle `LLMResult` and check `.is_fallback`.
- Propagate `is_fallback` through the finding dict: add an `"is_fallback": true/false` field alongside `"confident"` and `"loops_used"` in both the explanation step and the fix-generation step.

### Fix Part 2 — Never label fallback output as "Confident" or plain "Verified"

In `src/report/formatter.py`:
- If a finding's explanation has `is_fallback: true`, override whatever the critic loop reported and force the badge to: `⚠️ Offline fallback (LLM unreachable) — not a model-generated assessment`, regardless of what `confident` says. A fallback response was never evaluated by a real critic, so `confident: true` should never be trusted or displayed as-is when `is_fallback` is true.
- If a fix's generation had `is_fallback: true`, append to the verification line: `(Note: fix was generated by a rule-based fallback pattern, not the LLM — mechanical gates below still verify syntactic/structural correctness only)`.
- Add this same `is_fallback` field to the JSON output schema so downstream consumers (like the eval harness) can check it programmatically, not just read it in prose.

### Fix Part 3 — Change default behavior to fail loudly instead of silently falling back

In `main.py` (or wherever the LLM client is instantiated):
- Add a new CLI flag: `--allow-offline-fallback` (boolean, default `False`).
- If Ollama (or whichever configured backend) is unreachable and `--allow-offline-fallback` is NOT set, the program should stop immediately with a clear error and non-zero exit code:
  ```
  Error: LLM backend 'ollama' is unreachable (Connection refused).
  Start it with `ollama serve` and ensure the configured model is pulled,
  or re-run with --allow-offline-fallback to use a deterministic rule-based
  fallback for testing purposes (NOT equivalent to real model output).
  ```
- Only if `--allow-offline-fallback` is explicitly passed should the pipeline proceed using the deterministic fallback — and even then, every report/JSON output must carry the fallback labeling from Fix Part 2.
- Add the same check at the very start of `main.py` (a quick connectivity check before running static analysis at all), so you don't waste time running Slither only to fail on the first LLM call deep in the pipeline.

### Fix Part 4 — Protect the eval harness from silently mixing fallback and real results

In `eval/run_eval.py` (Step 20/29):
- Before computing precision/recall/F1/fix-success-rate, check whether ANY finding across the labeled set has `is_fallback: true`.
- If any are found, refuse to report aggregate metrics and print a clear error: `"Eval run contains N fallback-generated findings — results are invalid. Re-run with Ollama confirmed active."`
- This prevents accidentally publishing/quoting eval numbers that were partly generated by hardcoded rules instead of the actual system being evaluated.

### Verification
1. Stop Ollama (`ollama stop` or kill the process) and run the pipeline without `--allow-offline-fallback` — confirm it fails immediately with the clear error message above, before running static analysis or producing any report.
2. Run again with `--allow-offline-fallback` explicitly set — confirm the report clearly marks every finding as offline-fallback-generated, with no "Confident" or plain "Verified" labels appearing anywhere.
3. Start Ollama properly (`ollama serve`, confirm reachable via `curl http://localhost:11434/api/tags`), then re-run normally (no flag) — confirm it now succeeds and reports show genuine confidence/verification labels with `is_fallback: false`.
4. Attempt to run `eval/run_eval.py` against a labeled set where you've deliberately forced one fallback result — confirm it refuses to output aggregate metrics and shows the warning.

## Summary for the Coding Agent

| File | Change |
|---|---|
| `src/llm/llm_client.py` (and backend-specific clients) | Return a structured result with `is_fallback` and `fallback_reason`, not a bare string |
| All pipeline call sites using `llm.generate(...)` | Update to handle the structured result and propagate `is_fallback` into finding/fix dicts |
| `src/report/formatter.py` | Override confidence/verification badges with explicit offline-fallback labeling whenever `is_fallback` is true |
| `main.py` | Add `--allow-offline-fallback` flag (default off); fail loudly with a clear error if the LLM backend is unreachable and the flag isn't set; add an early connectivity check before running static analysis |
| `eval/run_eval.py` | Refuse to compute aggregate metrics if any finding in the run used the fallback; print a clear warning instead |

## Important Note Before Trusting Any Prior Results
Any report, JSON output, or eval numbers generated before this fix — including the `reentrancy_example.sol` and `unseen_test_example.sol` runs already produced — should be treated as **not representative of real LLM performance**, since both runs show the fallback firing. Re-run your full test batch only after confirming Ollama is live (Step 1 of Verification above) and this fix is in place.
